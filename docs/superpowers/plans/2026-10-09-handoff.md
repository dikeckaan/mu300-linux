## INCIDENT, 2026-10-09 ~12:40 — v2026.10.12 and v2026.10.13 WITHDRAWN (read this first)

The user reported, from a device on one of today's releases: hours of `sprd-wlan` errors (`WCN PCIEWARN
edma_pending_q_buffer(10) full`, `sc2355_pcie_push_link: push link fail: -1, chn: 10`, `tx_handle_to_send_list: tx
return err`, `reorder_msdu: seq_num < win_start`) then a reboot (uptime 12592 s -> boot). Done at once: both releases
set to prerelease, **v2026.10.11 is latest again**, a WITHDRAWN banner on both releases' notes. A device on them goes
back with `mu300-update rollback && mu300-update rollback-boot && reboot`.

What v2026.10.13 added over 10.12: the trustos image gone from the tree (now https://archive.org/details/zte-f50-mu300-trustos-ZYV1.0.0B09,
sha256 verified), `apk upgrade` in `openwrt/build-rootfs.sh` (LuCI 26.280, mbedtls 3.6.7, iwinfo 2026.05.26 in the images;
PR #82), docs (PR #83). The VPN toolkit (PR #76) and the users' reports fixes (PR #80) are in it too.

Facts so far (device / release / kernel of the reporter NOT known yet - ask): the 5.4 kernel bundle of 10.12 has
byte-identical Wi-Fi/WCN modules to 10.11 (sprd_wlan.ko, sprd_wlan_combo.ko, wcn_bsp.ko, sc2355_sdio_wlan.ko), so on 5.4
only userspace moved: wpad/hostapd 2025.08.26 r2 -> r5 (feed), `mu300-power` (PR #62: hotspot/radio/LED idle, charge guard),
the TTL tc backend. On 6.18/7.2 the kernel changed around exactly this hardware (PR #62/suspend-drivers, FINDINGS 37):
`upstream/modules/wcn_bsp/platform/sysfs.c` **armlog_status = 0** (the firmware's ARM log off by default - the one change
that alters firmware behaviour while awake; `echo 1 > /sys/devices/virtual/misc/wcn/devices/armlog_status` restores it),
`wcn_bsp/pcie/pcie.c` no `wcn_set_armlog(true)` after resume, `sprd_wlan_combo/common/iface.c` WoWLAN "any" by default,
`port/drivers/pci/controller/dwc/pcie-sprd.c` WAKE# IRQ without IRQF_NO_SUSPEND and wakeup only when armed,
`mu300-mainline.config` +CONFIG_SUSPEND/PM_SLEEP/PM_WAKELOCKS/**PM_AUTOSLEEP**/NO_HZ_IDLE/HIGH_RES_TIMERS. A load test on
F50-B (6.18, Wi-Fi client, ~800 MB download) was started to look for the errors; the U30 (7.2, 43 min up) and F50-B showed
none at the time.

**Result (13:40): NOT a regression.** The reporter has no device at hand (second-hand report; no log available). Reproduced on
F50-B (6.18, Wi-Fi client, 570 MB download at 19 MB/s through wlan0): the same lines come on every kernel - v2026.10.13
kernel 51 lines, with armlog on 48, **v2026.10.11 kernel 23 and 68** (two runs; the armlog sysfs write takes effect live).
The download finishes at full speed every time, no reboot, nothing else in dmesg. So `edma_pending_q_buffer(10) full` /
`push link fail` / `tx return err` are the vendor driver dropping TX packets when its queue to the chip is momentarily
full under sustained load, on 10.11 as much as on 10.13; they do not explain the reporter's reboot after 3.5 h (cause
unknown: no log). F50-B is back on the 10.13 boot image. Decision on re-promoting v2026.10.13 to latest is the user's;
recommended: re-promote (nothing found) and ask the reporter for `uname -r`, release and the log before the reboot.

Next: get the reporter's `uname -r`, release, system, full `logread`/`dmesg` before the reboot, `mu300-power status`,
