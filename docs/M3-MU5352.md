# ZTE M3 (MU5352): U30 Air hardware profile

ZTE M3 and ZTE U30 Air are separate device models. The device owner reports that they share the same hardware
design, with the M3 omitting NFC. Reusing the `u30air` implementation is distinct from the user-facing model name.

The M3 tested here reports `ro.product.model=MU5352`, `ro.product.device=MU5352`, and
`ro.board.platform=ums9620` on Android. Only that exact combination is recognized. The name "M3" by itself,
M3 Pro, and other platforms do not enable this alias.

The installers and boot-chain checks use the existing `u30air` profile. This keeps the U30 Air battery,
charger and USB code paths and the default LAN address `192.168.78.1`; it does not introduce a new kernel or
claim that every M3 feature is identical to a U30 Air's. The GUI recognizes Android's MU5352 adb record too.
Existing commands, services, modules, volume labels, kernel identifiers and `u30air` paths retain their names.

The device-side installer records `m3` in `/etc/mu300/device-model` from Android's properties, after settings
have been carried over. This is a model label, never a hardware override:

* `mu300-device` still prints `u30air`;
* `mu300-device --model` prints `m3`, and `--json` adds `model: "m3"` next to `device: "u30air"`;
* OpenWrt's hardware init sets the user-facing board name to `ZTE M3 (MU5352)`;
* `mu300-nfc supported` reports unsupported on M3 before touching NFC GPIO or I2C, while U30 Air behavior stays as before.

The marker is in `/etc/mu300`, which updates preserve. It is only used on the existing U30 Air path; reinstalling
on a U30 Air clears a carried-over M3 label. Other device paths are left alone, including their existing JSON
output, configuration and behavior.
Existing installations made before this change have
no marker and continue to report the U30 Air profile until installed/updated from Android with this installer.

## Device run, 2026-10-29

Tested on an MU5352 with Android `MU5352_DSV1.0.0B18`, board `ums9620_2h10_feimao`, about 29.1 GiB of eMMC,
Root and patched TrustOS, with the bootloader still locked. Android was on slot B; Linux was installed on A.
The installation used v2026.10.28.1, OpenWrt 25.12.6 with the cellular LuCI panel, and the 7.3.0 kernel bundle.

Verified on this device:

* exact model recognition, the boot-chain check, and installation to an already prepared 4 GiB eMMC region;
* OpenWrt boot, password login over SSH and LuCI, and a 5 GHz WPA2-PSK hotspot;
* modem registration reported 5G, the WAN interface was up, and an HTTP fetch from the device succeeded;
* battery and charger telemetry through the existing U30 Air handlers;
* OpenWrt -> Android B -> OpenWrt A, including Android Root and TCP adb, and an unchanged Android `boot_b` hash;
* China (`CN`) automatic channel selection with VHT80, `acs_exclude_dfs=1`, and the non-DFS candidate list
  `36 40 44 48 149 153 157 161`: hostapd logged ACS completion on 157 and then 149, and the client reconnected.

The owner additionally tested the buttons and reports normal operation matching the U30 Air. M3 has no NFC;
NFC operations are not expected to work and its capability check returns unsupported. USB networking/adb over
an actual cable, USB host/PD, LEDs, charging behavior and the other kernels or distributions were not validated
on this M3. They are not implied by selecting the U30 Air profile.

On 2026-10-30, the runtime identity scripts in this change were applied to that installed image. After a normal
reboot, `mu300-device --json` reported `device: "u30air", model: "m3"`, both `ubus call system board` and the
cellular dashboard reported `ZTE M3 (MU5352)`, CN/VHT80 automatic selection completed on channel 149 with DFS
excluded, and the WAN was up. This was a runtime-script check on the image above, not a rebuilt image of main.

WPA3-SAE remains disabled, as on the other SC2355 devices; see [U30AIR-SAE.md](U30AIR-SAE.md). A model alias does
not make the firmware key handoff safe. Automatic channel selection runs when the AP starts/reloads; it is not
continuous background channel hopping.

The stock installer can still reset Android when making room on a 32 GB device. The device run above began with
an already prepared free region; it does not validate the stock reset workflow or add a data-preserving shrinker.
Keep the normal backup, Root and TrustOS prerequisites. No firmware, proprietary Android files, keys, credentials,
IMEI, serial numbers or full device backups belong in a contribution.
